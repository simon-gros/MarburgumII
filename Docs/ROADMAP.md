# Milestone roadmap — MMORPG-first from Stage 0

**Reviewed through 12 November 2026 at `c5d41efc` (ADR-059):** [current development-state review](DEVELOPMENT_REVIEW_2026-11-12.md), [11 November audit](DEVELOPMENT_UPDATE_2026-11-11.md), [prior review](DAILY_CHANGE_REVIEW_2026-11-10.md). Source implementation, scoped editor smoke, prior packaged tests, current asset-sealed package and **explicit owner acceptance** are separate states. No new Unreal runtime test was conducted as part of the documentation review.

**Controlling rule:** MarburgumII preserves the majority of original Marburgum world/gameplay requirements but reimplements them in fresh Unreal Engine **5.8.3** C++ code. Dedicated authoritative client/server must be present in the **first running milestone**. “Solo-friendly” describes game experience, **not client authority or an offline-only code path**. See [NETWORK_ARCHITECTURE.md](NETWORK_ARCHITECTURE.md), [ONTOLOGY.md](ONTOLOGY.md), [UI_HUD_ONTOLOGY.md](UI_HUD_ONTOLOGY.md), [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md) and [LEGACY_PARITY.md](LEGACY_PARITY.md).

## Stage 0A — Native engine and role separation

Initially delivered as source, then **built and qualified on Linux**: `MarburgumII.uproject`, core/shared/client/server module descriptors, Client/Server/Editor/Game build targets, engine version pin, a server-owned GameMode and replicated GameState contract marker, .NET source-manifest verifier, Rust crate and baseline CI.

**Linux status (2026-11-08): passed.** Editor, Server, Client and the packaged LinuxServer/LinuxClient builds compile and link with UE 5.8.3. The Editor launches and loads the startup map, the headless server loads its modules, and symbol inspection confirms there is no side-to-side linkage ([evidence](STAGE0_EVIDENCE.md)). **Still outstanding:** a Windows build of the same targets.

## Stage 0B — Minimal actual online session (before gameplay)

One dedicated server plus one client, then two clients, join the same small test map using the same authoritative World/GameState. Verify the replicated contract version, joint visibility of server-owned state, clean disconnect and reconnect, and rejection of unauthorized client mutation. Record command line, binary build SHA and logs; run as distinct processes, not merely standalone PIE.

**Gate:** repeatable, observed server/client data path and networked authority. No account backend or persistence is claimed before they actually exist.

**Linux status (2026-11-08): passed on loopback.** `scripts/net-smoke-linux.sh` runs a packaged headless server with one client (refused mutation, idempotent operation, disconnect and reconnect), then two concurrent clients ([evidence](STAGE0_EVIDENCE.md)). Rendered-client joins are now captured by the Stage 0C UI evidence below.

## Stage 0C — Premium modular graphical UI and early chat foundation (UI-00 through UI-03 in parallel with Stage 0B)

Begin the client-facing visual system as soon as the native Editor/Client builds are available, **alongside** the dedicated server and two-client work rather than after all networking or content production. Preserve original Marburgum HUD semantics but rebuild the appearance professionally in UE **5.8.3**: responsive UMG theme, branded connection/transition screens, low-clutter exploration HUD, contextual prompt, location banner, one pinned objective, condition display, graphical notifications, and coherent on-demand Character, Skills, Inventory and Journal shells. The UI must consume replicated/server-owned state when present, with honest empty/loading/error states; static fixtures cannot masquerade as live MMO gameplay. Also add an early low-clutter [general/private text chat](CHAT.md): general to everyone on the connected logical server, and private conversation delivered **only to sender and intended recipient**, with server validation and client UMG presentation.

**Exclusions:** do not import the original wanted stars, wanted/heat levels, police pursuit/chase system or chase-specific HUD. Do not restore generated talents or Talent screens.

**Gate:** complete UI-00 ontology/parity validation and proceed through UI-01 (actual UMG tokens/gallery), UI-02 (session/focus shell) and initial UI-03 (modular, authority-aware HUD). Each has a separate runtime and screenshot gate; the complete server-connected public capture remains Stage 1. See [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md) and [UI_HUD_DESIGN.md](UI_HUD_DESIGN.md).

**Linux status (2026-11-08): UI-01 and UI-02 first implementation captured, awaiting owner playtest.** Design tokens, UMG primitives and a SAMPLE DATA gallery, plus the connection shell driven by a client session state machine on a no-authority front-end map (ADR-013), render in packaged clients from 720p to 4K. A packaged-server join, a connection timeout, and a real server stop/restart with automatic client recovery are captured ([evidence](STAGE0C_UI_EVIDENCE.md)). Focus traversal, the UI-scale matrix and a visual design review remain open.

**UI-03 / CHAT-001 (10 November): actual live modules now qualified in Linux smoke tests, pending personal owner approval.** General/private `chat_panel` and receipt notifications passed the three-client delivery/isolation test ([chat evidence](STAGE0C_CHAT_EVIDENCE.md)). Additional server-backed UI now includes item/NPC/vehicle `interaction_prompt`, district `location_banner`, saved `pinned_objective`, `player_condition` for stamina/swimming/drowning and contextual `vehicle_status` with speed/REV. Character, Inventory and Journal first UMG shells exist. Settings, final accessibility/focus/resolution matrix and personal owner review are open; first Skills and account/creator implementations now exist (ADR-047/055/057) ([UI roadmap](UI_HUD_ROADMAP.md)).

## Stage 0D — Licensed world-map acquisition and safe intake (parallel, nonblocking)

**Current default world is the original Unreal Lent map, `/Game/World/lent`**, selected by the owner after the first façade playtest (ADR-027). At the owner's request it now covers Lent and its eight neighbouring windows of the original, a 1,536 m square (ADR-045): ljudski_vrt, center, avtobusna, pristan, titov_most, kurilnica, magdalena and pobreška, with 870 closed-shell buildings, Titov most, the railway bridge, Studenška brv and one surveyed ground with paved streets. It already contains the original landscape, river, bridge and building layout; subsequent façade and closed-roof-shell repairs (ADR-034) require their own visual review. The **LiDAR-generated building-shell replacement** was reverted; ARSO **LiDAR terrain elevations** are now intentionally used for the current ADR-040/045 ground, a separate decision. Survey-based paved streets have real collision. ADR-053/054 subsequently smooth paving/verges/banks, fit islands, revise water and roof/plaster colours, add façade bands and build a **noncolliding distant ring**; they have editor geometry/visual evidence, not packaged frame-time proof. 2014 heights and 2026 OSM roads still need 1990s review. `/Game/Maps/Lent` is an **older separate** smoke-test map. The [TurboSquid city model](WORLD_MAP_ADOPTION.md), product 1639711, is an unpurchased/unimported candidate for *later* broader city geometry, not the active map, and may replace it only after provenance, historical/geospatial, performance, route and owner-approval gates. Never publish paid geometry.

**World-source gate:** purchase and rights, precise origin/landmark crosswalk, UE 5.8.3 local import, period corrections, collision/navigation, angler/mission, swim/wade and hatchback drive/exit regressions, frame-time and cooked-asset evidence, then **explicit owner approval**. Until approved, preserve `/Game/World/lent` as default and `/Game/Maps/Lent` for historic mission smokes.

## Stage 0F — Email-verified accounts, first character and entry gate (new prerequisite for public Stage 1)

**Status (2026-11-12): FL-A–FL-D implemented and editor-qualified, while FL-E is only partly tested; packaged and owner acceptance remain open ([ADR-055](DECISIONS.md), [ADR-057](DECISIONS.md)).** A self-hosted HTTPS account service (`services/accounts`) owns email codes, Argon2id passwords, sessions, the one character and single-use admission tickets. The client's screens cover sign-in, registration, code confirmation, credentials, password reset and the first character, with a full-height 3D preview of the chosen body that turns and zooms. A server started with `-MB2Accounts` admits only ticket holders, and they enter as their own character with their name and body. `scripts/account-smoke-linux.sh` proves the first-time and returning flows and five refused admissions. Still open: Slovene copy, complete keyboard/controller and packaged 720p–4K screen matrix, service deployment/real mail sender, suppression or mitigation of spent tickets in engine join-URL logs, full negative cases and owner approval. The sender is deferred to the first hosted service deployment (ADR-057).

Restore the original Marburgum's email-confirmed registration experience in a fresh secure service: new user verifies email, establishes a unique username/password, signs in, then **must create a character by choosing First name, Last name and one approved model**. Only a successful durable save and a dedicated-server entitlement/admission check permits world entry. Returning users authenticate and resume the same character without remaking it. Full specification: [FIRST_LAUNCH_ONTOLOGY.md](FIRST_LAUNCH_ONTOLOGY.md), machine catalogue [first_launch.v0.1.json](../Data/Ontology/first_launch.v0.1.json), and UI-02A in [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md).

**Delivery slices:** FL-A account/email/password verification and recovery; FL-B production-quality login/registration screens; FL-C 3D model preview and First name/Last name creator; FL-D idempotent persistent character binding and server-enforced world-admission authorization; FL-E reconnection, abuse/negative tests, packaged-client UI matrix and owner playtest. Protect login credentials, normalize and validate names server-side, and do not permit an invented client-side character or map-travel bypass. The existing ADR-014 development character key and file world store remain strictly named smoke-test adapters and are not substitutes for authentic credentials.

**Gate before first publicly accepted playable Stage 1 experience:** a new user completes FL-01–FL-12, including verification, login, character creation, save/restart/returning-user, unauthorized direct join rejection, rendered-client captures and personally approved owner playtesting on a freshness-verified UE 5.8.3 build. The current Gate 1/Lent/condition test slices can continue as explicitly **development-only tests** while this prerequisite is unbuilt. Stage 4 still owns production scale, anti-abuse operations, backups and service maturity, but **cannot be the first delivery of player-facing login and account-to-character admission**.

**Player condition status (2026-11-10): qualified on Linux, awaiting owner playtest.** The original game's breath rule is carried over ([ADR-020](DECISIONS.md)). The swim cycle starts from the original's own on the mannequin skeleton, with the body lying along the water and a flutter kick while it moves ([ADR-033](DECISIONS.md)) and upright, treading water, while it does not ([ADR-036](DECISIONS.md)); the GTA placeholder clip and the original's GTA placeholder water sounds are not imported, so swimming is silent. ## Working rules

- Every personal playtest must use a **freshness-verified UE 5.8.3 client/server archive containing the latest approved cooked assets**, with its SHA and asset digest recorded; see [PLAYTEST_FRESHNESS.md](PLAYTEST_FRESHNESS.md). Unverified previous builds are not valid acceptance evidence.
- Hunyuan3D-2.1 is a **conditional, legally gated local asset-production tool**; the official community license excludes the EU, so do not integrate generated outputs before applicable rights are established.

- A stage is not complete until it builds and executes under **UE 5.8.3** with its acceptance gate.
- **Every major playable feature requires the project owner's own in-game playtest and explicit recorded approval; automated checks are necessary but insufficient.**
- The purchased Maribor city model is the **planned** default geometry source only after verified acquisition/rights and owner qualification; never publish commercial source/derived meshes in GitHub.
- Never label a proposed system, data definition, source module or roadmap as working multiplayer.
- Reuse reviewed **requirements, ontology and provenance-audited game data** from original Marburgum; do not mechanically transplant Godot runtime code, server protocol, unreviewed assets or historical assumptions.
- No significant gameplay feature can bypass the client → authoritative server → replicated result boundary simply to simplify local testing.
- Every public-facing development capture must use a reviewed graphical UI and clearly distinguish functional gameplay from UI mockups.
- Intentionally excluded features (wanted stars, police pursuit/chases, legacy talents) are not implementation backlog items.
