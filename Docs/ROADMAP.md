# Milestone roadmap — MMORPG-first from Stage 0

**Reviewed 11 November 2026:** 47 commits over the preceding 24 hours, through `af2d0b3`; see the [daily change analysis](DAILY_CHANGE_REVIEW_2026-11-10.md). Implemented source, specific automated test, freshness-verified release candidate and **owner-approved gameplay** are distinct states.

**Controlling rule:** MarburgumII preserves the majority of original Marburgum world/gameplay requirements but reimplements them in fresh Unreal Engine **5.8.3** C++ code. Dedicated authoritative client/server must be present in the **first running milestone**. “Solo-friendly” describes game experience, **not client authority or an offline-only code path**. See [NETWORK_ARCHITECTURE.md](NETWORK_ARCHITECTURE.md), [ONTOLOGY.md](ONTOLOGY.md), [UI_HUD_ONTOLOGY.md](UI_HUD_ONTOLOGY.md), [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md) and [LEGACY_PARITY.md](LEGACY_PARITY.md).

## Stage 0A — Native engine and role separation

Initially delivered as source, then **built and qualified on Linux**: `MarburgumII.uproject`, core/shared/client/server module descriptors, Client/Server/Editor/Game build targets, engine version pin, a server-owned GameMode and replicated GameState contract marker, .NET source-manifest verifier, Rust crate and baseline CI.

**Linux status (2026-11-08): passed.** Editor, Server, Client and the packaged LinuxServer/LinuxClient builds compile and link with UE 5.8.3. The Editor launches and loads the startup map, the headless server loads its modules, and symbol inspection confirms there is no side-to-side linkage ([evidence](STAGE0_EVIDENCE.md)). **Still outstanding:** a Windows build of the same targets.

## Stage 0B — Minimal actual online session (before gameplay)

One dedicated server plus one client, then two clients, join the same small test map using the same authoritative World/GameState. Verify the replicated contract version, joint visibility of server-owned state, clean disconnect and reconnect, and rejection of unauthorized client mutation. Record command line, binary build SHA and logs; run as distinct processes, not merely standalone PIE.

**Gate:** repeatable, observed server/client data path and networked authority. No account backend or persistence is claimed before they actually exist.

**Linux status (2026-11-08): passed on loopback.** `scripts/net-smoke-linux.sh` runs a packaged headless server with one client (refused mutation, idempotent operation, disconnect and reconnect), then two concurrent clients ([evidence](STAGE0_EVIDENCE.md)). Rendered-client joins are now captured by the Stage 0C UI evidence below.

## Stage 0C — Premium modular graphical UI and early chat foundation (UI-00 through UI-03 in parallel with Stage 0B)

Begin the client-facing visual system as soon as the native Editor/Client builds are available, **alongside** the dedicated server and two-client work rather than after all networking or content production. Preserve original Marburgum HUD semantics but rebuild the appearance professionally in UE **5.8.3**: responsive UMG theme, branded connection/transition screens, low-clutter exploration HUD, contextual prompt, location banner, one pinned objective, condition display, graphical notifications, and coherent on-demand Character, Skills, Inventory and Journal shells. The UI must consume replicated/server-owned state when present, with honest empty/loading/error states; static fixtures cannot masquerade as live MMO gameplay. Also add an early low-clutter [general/private text chat](CHAT.md): general to everyone on the connected logical server, and private conversation delivered **only to sender and intended recipient**, with server validation and client UMG presentation.

**Exclusions:** do not import the original wanted stars, wanted/heat levels, police pursuit/chase system or chase-specific HUD. Do not restore generated talents or Talent screens.

**Gate:** complete UI-00 ontology/parity validation and proceed through UI-01 (actual UMG tokens/gallery), UI-02 (session/focus shell) and initial UI-03 (modular, authority-aware HUD). Each has a separate runtime and screenshot gate; the complete server-connected public capture remains Stage 1. See [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md) and [UI_HUD_DESIGN.md](UI_HUD_DESIGN.md).

**Linux status (2026-11-08): UI-01 and UI-02 first implementation captured, awaiting owner playtest.** Design tokens, UMG primitives and a SAMPLE DATA gallery, plus the connection shell driven by a client session state machine on a no-authority front-end map (ADR-013), render in packaged clients from 720p to 4K. A packaged-server join, a connection timeout, and a real server stop/restart with automatic client recovery are captured ([evidence](STAGE0C_UI_EVIDENCE.md)). Focus traversal, the UI-scale matrix and a visual design review remain open.

**UI-03 / CHAT-001 (10 November): actual live modules now qualified in Linux smoke tests, pending personal owner approval.** General/private `chat_panel` and receipt notifications passed the three-client delivery/isolation test ([chat evidence](STAGE0C_CHAT_EVIDENCE.md)). Additional server-backed UI now includes item/NPC/vehicle `interaction_prompt`, district `location_banner`, saved `pinned_objective`, `player_condition` for stamina/swimming/drowning and contextual `vehicle_status` with speed/REV. Character, Inventory and Journal first UMG shells exist. Full Skills/Settings, login/creator, accessibility, focus and resolution matrix are open ([UI roadmap](UI_HUD_ROADMAP.md)).

## Stage 0D — Licensed world-map acquisition and safe intake (parallel, nonblocking)

**Current default world is the original Unreal Lent map, `/Game/World/lent`**, selected by the owner after the first façade playtest (ADR-027). It already contains the original landscape, river, bridge and building layout; subsequent façade and closed-roof-shell repairs (ADR-034) require their own visual review. The generated LiDAR shell experiment was reverted. `/Game/Maps/Lent` is an **older separate** smoke-test map. The [TurboSquid city model](WORLD_MAP_ADOPTION.md), product 1639711, is an unpurchased/unimported candidate for *later* broader city geometry, not the active map, and may replace it only after provenance, historical/geospatial, performance, route and owner-approval gates. Never publish paid geometry.

**World-source gate:** purchase and rights, precise origin/landmark crosswalk, UE 5.8.3 local import, period corrections, collision/navigation, angler/mission, swim/wade and hatchback drive/exit regressions, frame-time and cooked-asset evidence, then **explicit owner approval**. Until approved, preserve `/Game/World/lent` as default and `/Game/Maps/Lent` for historic mission smokes.

## Stage 0E — Image-to-3D asset production readiness (parallel, conditional)

Owner-reported local Hunyuan3D-2.1 installation is a **potential** mesh/PBR texture pipeline for period urban props, vegetation and fish variants. Follow [ASSET_GENERATION_HUNYUAN3D.md](ASSET_GENERATION_HUNYUAN3D.md): the published community license excludes the EU, so **production generation/integration is blocked until applicable authorization is established**. Then inventory installation/checkpoints, validate source-image rights and test one generated asset through scale/retopology/UV/PBR optimization and UE 5.8.3 import. The source map remains the licensed Maribor geometry, subject to its own rights checks. Do not make core networking/UI work depend on this optional asset generator.

**Gate:** license cleared, verified local environment and one owner-approved in-game result. **Distinct already delivered asset path:** the protagonist was generated using local TRELLIS vertex-colour geometry, retopology and an independent Blender/Cycles bake (ADR-021/028/031/035/037/038). This does not clear Hunyuan3D licensing or provide multiple selectable public account models; see [character documentation](CHARACTER_PROTAGONIST.md).

## Stage 0F — Email-verified accounts, first character and entry gate (new prerequisite for public Stage 1)

**Planned, not implemented.** Restore the original Marburgum's email-confirmed registration experience in a fresh secure service: new user verifies email, establishes a unique username/password, signs in, then **must create a character by choosing First name, Last name and one approved model**. Only a successful durable save and a dedicated-server entitlement/admission check permits world entry. Returning users authenticate and resume the same character without remaking it. Full specification: [FIRST_LAUNCH_ONTOLOGY.md](FIRST_LAUNCH_ONTOLOGY.md), machine catalogue [first_launch.v0.1.json](../Data/Ontology/first_launch.v0.1.json), and UI-02A in [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md).

**Delivery slices:** FL-A account/email/password verification and recovery; FL-B production-quality login/registration screens; FL-C 3D model preview and First name/Last name creator; FL-D idempotent persistent character binding and server-enforced world-admission authorization; FL-E reconnection, abuse/negative tests, packaged-client UI matrix and owner playtest. Protect login credentials, normalize and validate names server-side, and do not permit an invented client-side character or map-travel bypass. The existing ADR-014 development character key and file world store remain strictly named smoke-test adapters and are not substitutes for authentic credentials.

**Gate before first publicly accepted playable Stage 1 experience:** a new user completes FL-01–FL-12, including verification, login, character creation, save/restart/returning-user, unauthorized direct join rejection, rendered-client captures and personally approved owner playtesting on a freshness-verified UE 5.8.3 build. The current Gate 1/Lent/condition test slices can continue as explicitly **development-only tests** while this prerequisite is unbuilt. Stage 4 still owns production scale, anti-abuse operations, backups and service maturity, but **cannot be the first delivery of player-facing login and account-to-character admission**.

## Stage 1 — Networked playable district and showcase-quality UI

Current owner-selected original Unreal Lent launch world `/Game/World/lent` (a future licensed map replacement requiring separate approval), player movement/camera, **high-quality visually finished initial graphical HUD**, interactable item and NPC, authoritative event/feedback, and a save/restart round trip. The original HUD's interaction/location/objective/condition/notification vocabulary and its Character/Skills/Inventory/Journal screens are carried into newly designed graphical interfaces rather than exposed as clumped debug text. Verify two clients cannot duplicate a limited item or gain unauthorized progress. Record a player-facing 1440p/4K gameplay capture after the networked loop works.

**Additional mandatory gate:** the project owner personally tests the playable world/interaction/HUD on the exact build and explicitly approves it; otherwise Stage 1 remains awaiting owner approval.

**Chat gate:** compile and run CHAT-001 on an actual dedicated UE 5.8.3 server with **three** separate clients (A→all general, A→B private, C never sees private), correct input focus, stale recipient handling, anti-spam checks and a documented personal owner playtest.

**Gate:** complete UI-03 live-HUD and UI-04 management-panel acceptance in [UI_HUD_ROADMAP.md](UI_HUD_ROADMAP.md): interaction → authoritative event/receipt → replicated state → restart → same outcome, with polished UI. Pass a responsive screenshot/interface-scale/focus matrix and a short *genuine* multiplayer-client capture. Static mockups or UI fixtures cannot close a gameplay gate.

**Gate 1 transaction status (2026-11-10): qualified on Linux with a test fixture, awaiting owner playtest.** A walkable test character presses E at a labeled test supply crate. The ServerOnly module validates the request (ADR-015), stores the grant in a file-backed world store before replicating it (ADR-014), and answers with a receipt. The HUD shows the `interaction_prompt`, receipt notifications and a first `inventory_view`. A packaged server and nine client sessions verify a failed disk write with no effect, a duplicate replay, an out-of-range refusal, two clients racing for the last unit (exactly one wins), restoration after a server restart, and refusal of keyless, duplicate and malformed characters ([evidence](STAGE1_GATE1_EVIDENCE.md)). The Lent slice below covers the district fallback, the NPC and the location/objective modules.

**Lent slice status (2026-11-10): the launch map is now the original Unreal Lent level, `/Game/World/lent` (ADR-027).** The generated LiDAR shells were rejected and reverted. The owner confirmed after the `0c06ce8` playtest that `/Game/World/lent` is the default map from now on. The angler and player starts are on that level. The façades are rebuilt, and they are not the final art. `/Game/Maps/Lent` remains the fallback the mission smokes use (ADR-016, detailed by ADR-024): the Lent promenade, the Drava and Stari most as an independently authored streetscape in the original game's coordinates. The 10 November qualification used the earlier flat blockout; the streetscape (shops, roofs, jetty, far bank) is a later authored pass and is not yet re-qualified by the packaged smoke. The server derives each player's area from the original `areas.json` box, and a `location_banner` shows it. The original riverside angler offers the original first story mission, "Something in the Water". Accepting it saves the mission and its start item in one commit (ADR-017), and the HUD shows a `pinned_objective` and a first `journal_panel`. A packaged server and five client sessions verify a failed write with no effect, a replay answered as a duplicate, the next step refused without a fish, a refusal from out of range and from a keyless client, owner-only mission progress, walking from the bridge into Lent, and restoration after a restart ([evidence](STAGE1_LENT_EVIDENCE.md)). Still open before **public Stage 1 approval**: FL-A–FL-E real authentication and owned-character admission, a fresh integrated run on the actual original Unreal `/Game/World/lent`, Skills/Settings and polished graphical focus/scale/accessibility matrix, 1440p/4K same-build captures, and the owner's personally recorded decision. Fishing is Stage 2 and blocks *completion* of the opening mission. Acquiring the proposed commercial map is a parallel candidate assessment, not an already implemented or automatic Stage 1 requirement.

**Player condition status (2026-11-10): qualified on Linux, awaiting owner playtest.** The original game's breath rule is carried over ([ADR-020](DECISIONS.md)). Walking is 2.2 m/s and holding Shift runs at 4.4 m/s. A run spends ten seconds of stamina and leaves the body winded, walking, until some breath is back. The server simulates it and corrects any client that claims otherwise. The condition is saved when a player leaves or the server stops. The HUD shows a `player_condition` card, and C opens a first Character panel. A packaged server and four client sessions verify the run, winding, walking while winded and the return of breath. They also verify an adversary that claims a full bar but is wound and held to walking, a winded save restored after a restart, a rested body saved as no entry, and a save at server stop ([evidence](STAGE1_CONDITION_EVIDENCE.md)). Drowning is the first thing that changes vitality (ADR-032).

**Swimming status (2026-11-10): qualified on Linux, awaiting owner playtest.** The original game's swimming, held breath and drowning are carried over onto the launch map's Drava ([ADR-032](DECISIONS.md)). Generated water volumes cover the river under its drawn surface. Holding a direction swims at 1.1 m/s with the mouth up, and letting go slips under. Held breath is the stamina bar, about a minute, and running out of it drowns the body. A drowned body waits a minute at the recovery point, and the wait is saved with it. The swim cycle starts from the original's own on the mannequin skeleton, with the body lying along the water and a flutter kick while it moves ([ADR-033](DECISIONS.md)) and upright, treading water, while it does not ([ADR-036](DECISIONS.md)); the GTA placeholder clip and the original's GTA placeholder water sounds are not imported, so swimming is silent. A dedicated server, a rendered swimmer, a remote observer and a restart verify it ([evidence](STAGE1_SWIM_EVIDENCE.md)). Still open: sounds, a river current, an underwater view, a plunge from height, a down pose and the owner playtest.

**Driving status (2026-11-10): qualified on Linux, awaiting owner playtest.** The original game's cars are carried over ([ADR-039](DECISIONS.md)): its five-car catalogue, its four-raycast handling as server-only physics, seats with doors behind the controller's RPCs, its driving keys and camera, and its own procedural bodywork and door clips. The prototype city hatchback (the Renault 4 GTL) is parked in `/Game/World/lent` where the original placed it. A parked car now holds on a slope, which the original's did not. A dedicated server, a rendered driver and a passenger verify the parked car, getting in, a refused seat, driving, steering, braking, reversing and getting out ([evidence](STAGE1_VEHICLE_EVIDENCE.md)). The GTA door clips and San Andreas engine sounds the original used as placeholders are not imported, so cars are silent. Still open: sounds, saving cars across restarts, ownership and fuel, traffic, damage, and the owner playtest.

**Fighting status (2026-11-11): qualified on Linux, awaiting owner playtest.** The original game's unarmed fighting is carried over ([ADR-041](DECISIONS.md)): its rules and numbers (jab, committed swing, held guard, stamina costs, cooldowns, stagger, reach and arc), its Lent fight cast at their original spots (a drinker who fights whoever hits him, two passers-by who step away) and its own guard, jab and swing clips on the mannequin. The server picks every target and applies every blow. A beaten body goes down and recovers, as a drowned one does. A downed NPC gets up after a minute, which the original's did not. Blows sound from a CC0 impact pack, because the original's fight sounds and hit and get-up clips were GTA placeholders and are not imported. The Unreal port's San Andreas wanted level and police stay out. A dedicated server, a client that is beaten down and a rendered client that fights the drinker to the floor verify it ([evidence](STAGE1_COMBAT_EVIDENCE.md)). Still open: hit reactions, weapons, perception, any consequence of a fight, NPC pathfinding, and the owner playtest.

**Street people status (2026-11-11): qualified on Linux, awaiting owner playtest.** The original game's ambient population is carried over ([ADR-044](DECISIONS.md)). Its groups, looks and its author's own reaction tables come unchanged. People appear out of sight round every player and walk a graph built from Lent's pavement. They flee, watch or ignore a fight, a run-over or someone lying in the street, and panic spreads through a crowd. They jump clear of a car or are knocked down by it, and some fight back when hit. San Andreas' decision weights and spawn bands and GTA III's wander are not imported; Marburgum II's own numbers replace them. A dedicated server with a rendered client that walks, swings at the air and drives into a probe verifies it ([evidence](STAGE1_STREET_EVIDENCE.md)). Still open: gunshots, traffic, time of day and everyday activities, sounds, more than one player, and the owner playtest.

## Stage 4 — MMORPG operations and capacity (not first server)

## Stage 5 — Narrative and production scale

Grow a finished **3–6-hour MMO-architected vertical slice** toward the original's ambitious ~75-hour authored campaign, more professions/skills, missions and city content. Maintain solo accessibility and small-group cooperation without fragmenting authoritative gameplay rules.

## Working rules

- Every personal playtest must use a **freshness-verified UE 5.8.3 client/server archive containing the latest approved cooked assets**, with its SHA and asset digest recorded; see [PLAYTEST_FRESHNESS.md](PLAYTEST_FRESHNESS.md). Unverified previous builds are not valid acceptance evidence.
- Hunyuan3D-2.1 is a **conditional, legally gated local asset-production tool**; the official community license excludes the EU, so do not integrate generated outputs before applicable rights are established.


- A stage is not complete until it builds and executes under **UE 5.8.3** with its acceptance gate.
- **Every major playable feature requires the project owner's own in-game playtest and explicit recorded approval; automated checks are necessary but insufficient.**
- The purchased Maribor city model is the **planned** default geometry source only after verified acquisition/rights and owner qualification; never publish commercial source/derived meshes in GitHub.
- Never label a proposed system, data definition, source module or roadmap as working multiplayer.
- Reuse reviewed **requirements, ontology and provenance-audited game data** from original Marburgum; do not mechanically transplant Godot runtime code, server protocol, unreviewed assets or historical assumptions.
- No significant gameplay feature can bypass the client → authoritative server → replicated result boundary simply to simplify local testing.
- Every public-facing development capture must use a reviewed graphical UI and clearly distinguish functional gameplay from UI mockups.
- Intentionally excluded features (wanted stars, police pursuit/chases, legacy talents) are not implementation backlog items.
